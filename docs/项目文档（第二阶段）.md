# 基于 MongoDB 的问卷系统——第二阶段项目文档

## 一、项目概述

### 1.1 项目背景与目标

本项目是“当代数据管理系统”课程大作业的第二阶段。系统在第一阶段基于 Flask 和 MongoDB 实现的问卷系统上进行扩展，保留用户认证、问卷创建与管理、题目配置、问卷发布、答卷提交、条件跳转、答案校验及问卷统计等核心流程，并围绕题目重复利用和版本管理增加功能。

第二阶段的需求变更集中在八个方面：

1. 保存常用题目，方便在不同问卷中重复使用。
2. 将题目分享给其他用户使用。
3. 修改题目时保护已经发布的问卷内容。
4. 记录题目修改历史，并支持查看来源关系和恢复旧版本。
5. 允许同一逻辑题目的不同版本同时存在，并供不同问卷使用。
6. 查询某个题目被哪些问卷使用。
7. 建立题目库，支持管理、添加和选用题目。
8. 按逻辑题目标识汇总同一道题在多个问卷中的回答情况。

第二阶段仍以现有后端 API 和 MongoDB 数据模型为基础进行改动，没有重新建立一套独立系统。本阶段的重点是让题目从“只属于某一份问卷的配置”扩展为可以保存、共享、形成版本、重复使用和跨问卷统计的业务对象。

### 1.2 项目范围

本阶段主要涉及后端逻辑、数据库组织、API 接口以及自动化测试。核心目标是验证题目复用、题目共享、题目版本管理、题库管理和跨问卷单题统计等功能与第一阶段原有问卷流程之间的关系。

本项目使用 Flask 处理 HTTP 请求，通过 PyMongo 访问 MongoDB，并使用 pytest 执行 API 自动化测试。当前已确认的测试记录为：完整自动化测试 40 项通过；使用 `question_stats` 关键字筛选的题目统计测试 4 项通过。

### 1.3 设计原则

1. **在原系统上扩展。** 保留第一阶段核心模块和业务流程，在此基础上增加题目库、逻辑题目标识和相关管理逻辑。
2. **区分逻辑题目与问卷中的题目实例。** 逻辑题目用于表达可重复利用的题目；问卷中的题目实例用于保存某一份问卷实际使用的题目内容和配置。
3. **避免修改历史问卷内容。** 对题目进行后续修改时，应通过新版本或新题目保存变化，防止已经发布的问卷内容被意外覆盖。
4. **由后端执行权限和数据校验。** 题目管理、题目分享、版本操作和统计查询都应检查当前用户及数据归属，不能仅依赖客户端传入的标识。
5. **沿用现有 MongoDB 数据组织方式。** 用户、问卷、题目、答卷等按业务职责组织，并通过业务标识关联。
6. **使用自动化测试检查回归。** 修改后运行完整测试，检查新增逻辑是否影响原有的问卷创建、答卷提交和统计功能。

## 二、系统说明

### 2.1 系统总体架构

第二阶段继续采用第一阶段的分层结构。Flask 应用接收 HTTP 请求，各路由模块完成业务处理，再通过数据库连接模块访问 MongoDB。

```text
用户 / HTTP 请求
        |
        v
Flask 应用（app/__init__.py）
        |
        +---- 用户认证（app/routes/auth.py）
        |
        +---- 问卷管理（app/routes/surveys.py）
        |
        +---- 题目管理（app/routes/questions.py）
        |
        +---- 题目库与题目复用相关功能
        |     （app/routes/question_library.py）
        |
        +---- 答卷提交与统计
        |     （app/routes/responses.py）
        |
        v
MongoDB 连接模块（app/db.py）
        |
        v
用户、问卷、题目、答卷及题目库相关数据
```

`run.py` 是应用启动入口；`app/__init__.py` 负责创建 Flask 应用并注册路由；`app/db.py` 负责读取数据库配置并创建 MongoDB 客户端；`app/init_db.py` 负责数据库初始化和索引创建。应用启动和数据库初始化相互独立，运行前先确认 MongoDB 服务可用，再按项目要求执行初始化。

### 2.2 主要模块职责

| 模块 | 主要职责 |
|---|---|
| `run.py` | 启动 Flask 应用 |
| `app/__init__.py` | 创建应用、加载配置、注册路由及提供基础接口 |
| `app/db.py` | 读取 MongoDB 配置、创建客户端并选择数据库 |
| `app/init_db.py` | 初始化数据库集合及索引 |
| `app/routes/auth.py` | 用户注册、登录、退出登录及登录状态查询 |
| `app/routes/surveys.py` | 问卷创建、列表查询、发布、关闭、截止时间、分享访问和问卷统计 |
| `app/routes/questions.py` | 问卷内题目的创建、查询、修改和删除 |
| `app/routes/question_library.py` | 题目库及题目复用相关业务处理；具体子接口以该模块实际注册的路由为准 |
| `app/routes/responses.py` | 答卷提交、答案校验、条件跳转路径验证，以及跨问卷单题统计接口 |
| `tests/test_api.py` | API 自动化测试 |

### 2.3 配置与运行方式

项目通过环境变量配置 Flask 密钥和 MongoDB 连接信息，主要包括：

- `SECRET_KEY`：Flask 会话等功能使用的签名密钥。
- `MONGO_URI`：MongoDB 服务连接地址。
- `MONGO_DB_NAME`：项目使用的数据库名称。

数据库连接模块通过 PyMongo 访问 MongoDB，并可使用 `python-dotenv` 加载环境变量。第一阶段项目文档记录的开发数据库默认名称为 `survey_system`，自动化测试使用 `survey_system_test`。运行测试前，应核对本地 `.env` 和测试配置，确保测试使用专门的测试数据库，避免影响开发数据。

在开发环境中配置独立的 `SECRET_KEY`，仅供开发的默认密钥不应直接用于正式部署。

## 三、第二阶段需求变更与功能设计

### 3.1 任务一：保存常用题目并重复使用

用户可以将经常使用的题目保存起来，在创建新问卷时再次选用。该需求减少重复录入，也为题目跨问卷统计提供基础。

主要业务流程为：创建或选择已有题目，将其保存到可重复利用的题目集合；创建新问卷时查询可用题目；选定题目后将其加入目标问卷；最后检查题目内容和问卷之间的关联是否正确。

设计上需要区分“题目模板或逻辑题目”和“问卷中实际使用的题目”。复用题目不应导致已有问卷的题目被意外覆盖。

### 3.2 任务二：分享题目给其他用户

题目分享功能允许题目创建者将题目提供给其他用户。被分享用户可以在自己的问卷中使用该题目，分享行为不应导致原创建者失去使用权。

此功能需要区分题目所有者、分享对象和题目使用者。后端应根据当前登录用户检查题目访问权限，并避免未获授权的用户修改或管理其他用户的题目。

### 3.3 任务三：修改题目时保护已发布问卷

已发布问卷中的题目内容应保持稳定。若后续需要修改题目，应生成新的题目或新版本，而不是直接改写已经发布的问卷快照。这样可以避免旧问卷的题目内容与已收集的答案失去对应关系。

这一规则与第一阶段“问卷发布后限制题目修改”的设计保持一致，并在第二阶段进一步用于题目复用和版本管理场景。

### 3.4 任务四：题目修改历史与版本恢复

系统需要记录题目修改历史，使用户能够查询历史版本，了解新题目与原题目之间的来源关系，并在需要时恢复旧版本。

版本历史应能表达题目先后变化的过程，例如初始版本、后续修改版本以及版本之间的来源或关联关系。恢复旧版本时，应按照系统的版本管理规则恢复内容，并保留必要的历史记录，避免恢复操作无意中抹去变更轨迹。

### 3.5 任务五：同一题目的不同版本共存

同一逻辑题目可以形成多个版本。各版本应可以分别识别和维护，不同问卷能够选择适合自己的版本。例如，一份问卷保留旧题，另一份问卷使用修改后的新题。

逻辑题目标识用于识别题目的共同来源或逻辑身份；版本标识则用于区分具体内容。跨问卷统计时，可依据逻辑题目标识聚合同一题目的回答，而题目内容展示、问卷快照和具体版本维护仍需区分版本。

### 3.6 任务六：查询题目被哪些问卷使用

系统需要根据目标题目查询相关问卷及使用关系，帮助用户在修改题目之前了解其影响范围。若题目已经被多个问卷使用，用户可以结合问卷状态和版本规则决定是否创建新版本。

查询时应检查数据归属和权限范围。返回结果应与实际题目使用关系一致，不应向当前用户泄露其无权查看的问卷信息。

### 3.7 任务七：题目库管理

题目库用于集中保存和组织可重复使用的题目。用户可以管理题库内容、将题目加入题库，并在创建问卷时从题库选题。题目库中的题目也应支持按照系统版本规则进行更新。

题目库与具体问卷之间的关系需要保持清晰：题目库负责提供可复用题目，问卷保存自身实际使用的题目内容和规则。更新题目库内容时，不应意外修改已经发布问卷中的题目。

### 3.8 任务八：跨问卷单题统计

第一阶段的问卷统计以单份问卷为范围。第二阶段增加跨问卷单题统计需求，以逻辑题目标识 `question_key` 为查询条件，汇总当前用户创建的不同问卷中同一逻辑题目的答题数据。

该功能由 `app/routes/responses.py` 中的接口提供：

```http
GET /api/responses/question-stats/<question_key>
```

统计时需要先确定当前用户有权查询的问卷范围，再筛选使用目标逻辑题目的答卷，并根据相应题型计算统计结果。返回数据包括统计对象；已核对的响应结构中，统计主体位于 `stats` 下，包含 `response_count`，数字题统计还包含 `numeric.average` 和 `numeric.count` 等字段。其他题型的具体统计字段应以当前接口实现返回的数据为准。

## 四、MongoDB 数据库设计

### 4.1 数据建模思路

本项目采用 MongoDB 作为数据库，使用文档模型保存问卷系统中的用户、问卷、题目、答卷及题目复用相关数据。第一阶段主要围绕问卷创建、题目配置、答卷提交和统计分析进行数据建模；第二阶段则在原有数据模型基础上，进一步考虑题目复用、题目分享、题目版本管理、题库管理、题目使用情况查询和跨问卷单题统计等需求。

数据库设计的主要逻辑：

**（1）按照业务对象组织数据。**

用户、问卷、题目和答卷具有不同的业务职责，因此将它们分别组织为相应的集合。这样可以独立查询和维护不同类型的数据，避免将所有业务信息存储在同一个大型文档中。

**（2）根据数据之间的关系选择嵌入或关联。**

对于依附于某个业务对象、通常需要一起读取的数据，可以考虑嵌入文档。例如，题目的选项、校验配置和跳转规则通常需要随题目一起读取，适合与题目配置放在同一文档中；一次答卷中的答案列表通常也需要整体保存。

对于具有独立查询和维护需求的业务对象，例如用户、问卷和答卷，则采用独立文档保存，并通过业务标识建立关联。

**（3）区分逻辑题目与问卷实际使用的题目内容。**

第二阶段要求同一题目能够被多个问卷重复使用，同时允许题目产生新版本。如果只通过修改一份共享题目的当前内容来满足所有问卷的需要，就可能导致已经发布的问卷发生意外变化。因此，数据库设计需要区分逻辑题目、题目版本和问卷中实际使用的题目内容，使题目复用与历史问卷内容保护能够同时实现。

**（4）由应用程序维护数据关联和权限。**

MongoDB 的文档关联不等同于关系型数据库中的外键约束。即使文档中保存了问卷标识、用户标识或题目标识，数据库也不会自动保证对应记录一定存在，或者执行请求的用户拥有操作权限。因此，系统需要在应用层检查关联对象是否有效、当前用户是否具有相应权限，以及题目版本和问卷之间的关联是否符合业务规则。

**（5）围绕实际查询设计索引。**

问卷系统的常见查询包括按用户名查找用户、按创建者查询问卷、按问卷标识查询题目和答卷，以及按逻辑题目标识汇总统计数据。索引设计应结合这些实际查询需求，兼顾查询效率、数据唯一性和写入维护成本。

### 4.2 核心数据集合

第一阶段的数据库主要包含 `users`、`surveys`、`questions` 和 `responses` 四类核心集合。第二阶段增加了题目复用、分享、版本管理和题库管理等业务需求，需要进一步区分相应的逻辑数据。

| 集合或业务数据 | 主要内容 | 主要用途 |
|---|---|---|
| `users` | 用户名、密码哈希等 | 用户注册、登录和身份识别 |
| `surveys` | 创建者、标题、描述、问卷状态、分享码、截止时间及时间字段等 | 问卷的创建、发布、关闭和归属管理 |
| `questions` | 所属问卷、题目标题、题型、选项、必填规则、校验配置、跳转规则和顺序等 | 保存问卷使用的题目配置，并支持问卷题目查询和维护 |
| `responses` | 所属问卷、提交者标识、答案列表和提交时间等 | 保存答卷，为问卷统计和跨问卷单题统计提供数据 |
| 题目复用相关数据 | 可复用题目及其逻辑标识、版本关联等信息 | 支持常用题目保存、重复使用和版本区分 |
| 题目分享相关数据 | 题目所有者、共享对象或其他用于判断共享权限的信息 | 控制题目分享及被分享用户的访问和使用权限 |
| 题库相关数据 | 题库中的题目及其关联信息 | 支持题库管理、添加题目、从题库选题和题目更新 |

上表中的前四项是第一阶段文档记录的核心集合。后四项主要从第二阶段的业务概念出发进行说明。题目复用、版本和分享信息可以采用不同的物理存储方式，具体应以 `app/routes/question_library.py`、`app/init_db.py` 及相关数据库操作代码为准。

MongoDB 中的文档还包含自动生成的 `_id`，用于标识具体文档。业务层中的问卷标识、题目标识和逻辑题目标识则承担不同的关联作用。

### 4.3 核心数据结构与字段职责

#### 4.3.1 用户数据

用户数据保存在 `users` 集合中，主要用于识别系统用户、建立登录会话以及判断相关业务数据的所有者。

| 字段或数据 | 作用 |
|---|---|
| `_id` | MongoDB 文档标识 |
| `username` | 用户名，用于用户识别和登录 |
| 密码哈希 | 保存经过哈希处理的密码信息，而不是直接保存明文密码 |
| 其他用户信息 | 根据当前代码中实际维护的字段确定 |

用户名应具有唯一性，避免不同用户使用相同用户名注册。用户标识还用于关联问卷的创建者，以及题目分享和题库功能中的用户权限。

数据库中保存用户标识并不意味着可以仅凭该标识允许操作。每次管理请求仍需由后端验证当前登录身份及相应资源的所有权或访问权限。

#### 4.3.2 问卷数据

问卷数据保存在 `surveys` 集合中。每份问卷是独立文档，保存问卷的基本信息、创建者、生命周期状态和访问相关信息。

| 字段或数据 | 作用 |
|---|---|
| `_id` | 问卷文档标识 |
| `creator_id` | 标识创建问卷的用户 |
| `title` | 问卷标题 |
| `description` | 问卷描述 |
| `status` | 表示问卷当前状态，例如 `draft`、`published` |
| `share_code` | 用于通过分享码定位问卷 |
| `deadline` | 问卷截止时间；具体可选性以实际实现为准 |
| `created_at` | 问卷创建时间 |
| `updated_at` | 问卷更新时间 |
| 其他配置 | 根据当前代码中的实际字段确定 |

问卷状态用于控制问卷的业务生命周期。草稿问卷可以继续配置题目；满足发布条件后可以发布；已发布问卷可以在符合条件时关闭。分享码用于访问问卷，但具体能否访问和提交，还需要结合问卷状态和截止时间判断。

创建者标识用于限制问卷管理范围。用户查询自己的问卷列表时，应根据当前登录用户的标识进行过滤，避免返回其他用户的私有问卷管理数据。

#### 4.3.3 题目数据

题目配置保存在 `questions` 集合或当前代码定义的相关题目存储结构中。第一阶段的题目主要与单份问卷关联，第二阶段则进一步引入逻辑题目标识、题目复用和版本管理等概念。

| 字段或数据 | 作用 |
|---|---|
| `_id` | 当前题目文档的标识 |
| `survey_id` | 标识题目所属的问卷 |
| `title` | 题目标题 |
| `type` | 题目类型，例如单选、多选、文本和数字 |
| `options` | 选择题的选项数据 |
| 必填配置 | 控制题目是否必须填写 |
| 校验配置 | 保存文本长度、数字范围或选项数量等限制 |
| 跳转规则 | 保存条件跳转的判断条件和目标题目等信息 |
| `order` | 题目在问卷中的显示顺序 |
| 时间字段 | 记录题目创建或更新的时间；具体字段以当前实现为准 |
| `question_key` | 第二阶段跨问卷单题统计所使用的逻辑题目标识 |

题目类型决定其配置和答案校验规则。例如，选择题需要维护选项，文本题可以配置长度限制，数字题可以配置数值范围。将相关规则与题目配置一起管理，有助于后端在提交答卷时根据题目定义检查答案。

需要特别区分题目标识的不同用途：

- **题目文档标识**用于定位某一条具体题目记录。
- **逻辑题目标识**用于识别同一逻辑题目在不同使用场景中的关联关系。
- **问卷标识**用于确定题目属于哪份问卷。

对于题目复用和跨问卷统计，仅凭不同问卷中的题目文档标识可能无法识别这些题目是否属于同一逻辑题目，因此需要通过逻辑题目标识建立相应关联。

上述内容说明的是字段或业务数据的职责；对于没有在当前代码中核实的具体字段名称、字段类型和存储位置，应以实际实现为准。

#### 4.3.4 答卷数据

答卷数据保存在 `responses` 集合中。每次成功提交通常形成一份独立答卷文档，使系统能够保留每次提交的结果，并据此进行统计。

| 字段或数据 | 作用 |
|---|---|
| `_id` | 答卷文档标识 |
| `survey_id` | 标识答卷所属的问卷 |
| `respondent_id` | 保存提交者标识；匿名问卷按实际实现处理 |
| `answers` | 保存本次提交的答案列表 |
| `submitted_at` | 记录答卷提交时间 |

答案列表中的每个答案项主要通过题目标识关联对应题目，并保存实际答案内容。第一阶段文档中记录的答案项包括 `question_id` 和 `answer`。

将一次提交的答案组织在同一份答卷文档中，可以较方便地保存和查询一次完整提交的结果。题目选项和答案内容具有动态性，因此使用文档和数组结构可以适应不同题型的数据差异。

题目逻辑标识与答卷中题目标识的具体保存方式，会影响跨问卷统计的实现。统计时应依据当前数据库结构和实际查询逻辑，确认如何将某次答卷中的答案与对应的逻辑题目进行关联，而不是仅依赖题目标题进行匹配。

### 4.4 主要数据关联关系

第一阶段的核心关联关系可以表示如下：

```text
users
  |
  | creator_id
  v
surveys
  |
  +---- questions
  |       通过 survey_id 关联
  |
  +---- responses
          通过 survey_id 关联
```

用户可以创建多份问卷；每份问卷可以包含多道题目，也可以对应多份答卷。问卷与题目、问卷与答卷之间通过业务标识建立关联。

第二阶段的题目复用和版本管理进一步扩展了关联关系：

```text
                    逻辑题目
                       |
             +---------+---------+
             |                   |
          题目版本 A           题目版本 B
             |                   |
          问卷实例 A           问卷实例 B
             |                   |
          答卷中的答案         答卷中的答案

用户 ---- 题目所有权或分享关系
题库 ---- 题目或版本关联关系
逻辑题目标识 ---- 跨问卷统计查询
```

该图表示第二阶段需要表达的业务关系，不代表每个节点都必然单独保存为 MongoDB 集合。实际实现可能使用单独文档、嵌入字段或关联标识表达这些关系。

从数据一致性的角度看，应用程序至少需要关注以下问题：

1. 题目所关联的问卷是否存在。
2. 当前用户是否有权管理目标问卷或目标题目。
3. 分享用户是否具有所请求的访问或使用权限。
4. 题目版本之间的来源关系是否正确。
5. 问卷实际使用的题目内容是否与该问卷应保留的版本一致。
6. 跨问卷统计是否只汇总符合权限范围的数据。

由于 MongoDB 不会像关系型数据库那样自动执行传统外键约束，这些关联检查需要由业务代码负责。

### 4.5 题目复用、版本管理与历史数据保护

#### 4.5.1 逻辑题目与具体版本

第二阶段的题目管理需要区分逻辑题目和某一时点的具体题目内容。

逻辑题目表示一个可以被重复使用的题目概念，例如“你的年龄”；题目版本则表示该题目在某一次修改后形成的具体内容。两个版本可以具有相同的逻辑题目标识，但它们的题目内容、选项或校验配置可能不同。

通过这种区分，系统可以识别哪些题目属于同一逻辑题目，同时保留具体版本之间的差异。不同问卷可以根据需要使用不同版本，而不必强制共用同一份当前题目内容。

#### 4.5.2 题目内容的独立性

题目复用并不意味着所有问卷始终读取同一份可变的题目内容。

假设问卷 A 已经使用某一版本的题目，之后用户希望修改题目并用于问卷 B。如果直接覆盖原题目内容，问卷 A 中的题目可能发生变化，从而影响历史问卷内容与已收集数据之间的一致性。

因此，数据库设计应区分题目被复用时的关联关系，以及问卷实际使用的题目内容。修改题目时，应根据系统的版本规则创建或使用新的题目版本，并确保已经发布的问卷不会因为其他地方的题目更新而意外改变。

题目版本可以通过逻辑题目标识和版本关联信息组织。具体的版本字段、版本号规则以及是否采用单独的历史版本文档，需要根据当前项目代码中实际使用的结构说明。

#### 4.5.3 历史版本与恢复

题目历史记录用于保留修改前后的版本信息。若系统记录了版本来源、版本内容及必要的关联信息，就能够按照版本关系查询题目历史，并定位某一旧版本。

恢复旧版本时，需要明确恢复操作的含义。常见的设计方式是根据所选历史版本重新生成当前使用版本，而不是无条件删除中间版本。这样有利于保留修改过程，也可以降低直接覆盖历史数据造成的信息丢失风险。

### 4.6 题库与题目分享的数据设计

#### 4.6.1 题库数据

题库用于将常用题目集中组织起来，使用户在创建新问卷时能够查找和选用已有题目。

与直接在问卷中创建题目相比，题库强调题目的重复利用和集中管理。题库相关数据需要能够表达题目归属、题目内容或版本关联，以及题目能否被当前用户使用等业务信息。

题库中的题目与问卷中的题目承担不同的业务角色。题库负责保存和组织可供选用的题目资源，问卷中的题目则用于定义实际答题时展示的内容、校验规则和条件跳转行为。

如果系统支持题库题目的更新版本，就需要保证题库版本更新不会无意中改变已经发布的问卷。实际存储结构可以根据当前代码选择嵌入或关联方式，但需要清楚表达题库资源与问卷实际使用题目之间的关系。

#### 4.6.2 题目分享数据

题目分享功能用于允许其他用户使用共享题目。该功能不仅涉及题目内容，还涉及题目所有权和使用权限。

数据库设计应能够区分题目所有者、被分享用户，以及题目当前是否允许被访问或复用。用户通过分享获得使用权限，并不意味着自动拥有修改或删除原题目的权限。

在处理分享相关请求时，后端应检查题目是否存在、当前用户是否为所有者或获得授权的使用者，并根据相应权限决定能否执行操作。

题目分享关系可以根据实际实现存储为独立关系记录，也可以使用题目文档中的相关字段表达。

### 4.7 索引设计与查询优化

索引可以提高特定查询的效率，也可以对部分数据施加唯一性约束。不过，索引会增加数据写入和更新时的维护成本，因此应结合系统实际查询模式设计。

第一阶段项目文档记录的索引如下：

| 集合 | 索引名称 | 索引字段与作用 |
|---|---|---|
| `users` | `uq_users_username` | 对 `username` 建立唯一索引，避免用户名重复 |
| `surveys` | `uq_surveys_share_code` | 对 `share_code` 建立唯一索引，避免分享码重复 |
| `surveys` | `idx_surveys_creator_created` | 对 `creator_id` 和 `created_at` 建立组合索引，支持按创建者和创建时间查询问卷 |
| `questions` | `uq_questions_survey_order` | 对 `survey_id` 和 `order` 建立组合唯一索引，约束同一问卷内题目顺序不重复 |
| `responses` | `idx_responses_survey_submitted` | 对 `survey_id` 和 `submitted_at` 建立组合索引，支持按问卷查询答卷及提交时间 |
| `responses` | `uq_responses_submission_key` | 对 `submission_key` 建立稀疏唯一索引，仅对包含该字段的记录施加相应唯一性约束 |

以上索引名称和用途来自第一阶段项目文档。第二阶段新增字段是否建立索引，需要以当前 `app/init_db.py` 中的实际定义为准。

第二阶段的业务还涉及以下查询场景：

1. **逻辑题目查询。** 根据逻辑题目标识查找题目或对应版本。
2. **题目使用情况查询。** 查找哪些问卷使用了目标逻辑题目。
3. **题目分享查询。** 根据当前用户及分享关系查找有权使用的题目。
4. **题库选题。** 按用户权限和题目关联信息查询可复用题目。
5. **跨问卷统计。** 根据当前用户有权访问的问卷范围和逻辑题目标识，筛选符合条件的答卷及答案数据。

如果这些查询随着数据规模增大而成为性能瓶颈，可以依据实际数据组织方式评估复合索引。例如，当查询需要同时按问卷标识和提交时间过滤时，可以评估相应组合索引；当逻辑题目标识参与频繁查询或聚合时，可以评估与其实际存储位置匹配的索引。

需要注意，索引应根据字段在文档中的实际位置以及查询条件进行设计。如果逻辑题目标识位于嵌套数组中，索引还需要考虑 MongoDB 对数组索引的处理方式。不能仅因为某个字段参与业务查询，就认定项目已经为该字段建立了索引。

此外，第一阶段文档已经说明，`submission_key` 稀疏唯一索引不等于系统已经实现防重复提交。如果当前答卷提交代码没有写入该字段，就不能依靠该索引宣称能够限制同一用户重复提交。

### 4.8 跨问卷单题统计的数据来源与查询逻辑

第一阶段的统计功能主要以单份问卷为范围，通过问卷标识查询答卷，再按照题型统计提交结果。第二阶段增加了跨问卷单题统计，目的是汇总同一逻辑题目在多个问卷中的回答情况。

该功能的关键在于区分具体问卷中的题目标识与用于跨问卷识别的逻辑题目标识。不同问卷使用的题目可能对应不同的题目文档，但只要它们确实属于同一逻辑题目，就可以在满足权限要求的前提下进行汇总。

跨问卷统计的处理过程可以概括为：

```text
接收单题统计请求
        |
        v
获取当前登录用户
        |
        v
根据逻辑题目标识定位目标题目
        |
        v
确定当前用户有权统计的问卷范围
        |
        v
查找相关答卷及对应答案
        |
        v
按题目类型计算统计结果
        |
        v
返回统计数据
```

以上流程用于说明业务逻辑，不代表每一步都对应独立的数据库查询。实际查询和聚合步骤以当前 `app/routes/responses.py` 中的实现为准。

跨问卷统计需要特别关注数据范围。系统不能因为某个逻辑题目标识在其他用户的问卷中也存在，就将那些无权访问的答卷直接汇总。因此，统计条件必须与当前用户可统计的问卷范围相匹配。

在统计结果中，还应区分以下几类数量：

| 统计项目 | 含义 |
|---|---|
| 答卷数量 | 符合当前统计条件的答卷记录数量 |
| 数字答案数量 | 实际参与数字统计的有效答案数量 |
| 选项选择次数 | 单选或多选回答中某个选项被选择的次数 |
| 文本答案记录 | 符合统计条件的文本回答数据 |

对于数字题，如果存在空答案或无效数据，参与平均值计算的答案数量可能小于答卷总数。对于多选题，一份答卷可以选择多个选项，因此各选项的选择次数之和可能大于答卷数量。

当前项目已增加接口 `GET /api/responses/question-stats/<question_key>`，用于按逻辑题目标识查询跨问卷统计结果。相关自动化测试的已知执行结果为 4 项通过；完整自动化测试的已知执行结果为 40 项通过。上述结果说明对应测试运行成功，但不能单独证明所有统计边界情况均已覆盖。

### 4.9 数据一致性、权限与维护考虑

由于本项目通过多个集合和业务标识组织数据，数据库一致性不仅取决于数据本身，还取决于后端在新增、修改、分享和提交等操作中执行的检查。

首先，新增题目或建立题目关联时，应检查目标问卷和题目是否符合关联规则。其次，题目修改和版本恢复应遵循历史数据保护原则，避免已经发布的问卷内容因其他业务操作而发生变化。再次，题目分享、题库管理和跨问卷统计都需要检查当前用户的权限，避免通过猜测或直接提交业务标识访问无权使用的数据。

在维护方面，数据库初始化脚本负责创建项目定义的集合或索引，应用程序则负责执行业务规则。开发和测试时，应确保测试数据库与正常使用的数据库相互隔离，避免自动化测试清理数据时影响真实问卷或答卷。

### 5.3 第二阶段新增：跨问卷单题统计接口

#### `GET /api/responses/question-stats/<question_key>`

**用途：** 查询同一逻辑题目在当前用户有权查看的多个问卷中的回答统计。

**路径参数：**

| 参数 | 含义 |
|---|---|
| `question_key` | 用于标识逻辑题目的键，作为跨问卷汇总的查询条件 |

**处理过程：**

1. 接收 `question_key` 路径参数。
2. 根据当前登录用户确定可统计的问卷范围。
3. 查找该范围内使用目标逻辑题目的相关答卷。
4. 根据题型处理答案并计算统计值。
5. 返回包含统计结果的 JSON 数据。

**返回结构说明：** 已核对的响应形式以 `stats` 为统计结果主体，其中包含 `response_count`；数字题统计包含 `numeric.average` 和 `numeric.count` 等信息。其他题型返回字段应以当前接口实际实现为准。

**示意响应结构：**

```json
{
  "stats": {
    "response_count": 0,
    "numeric": {
      "average": null,
      "count": 0
    }
  }
}
```

以上数值仅用于说明字段结构，并非实际测试输出。实际接口会根据数据库中的答卷数据返回相应结果。

### 5.4 题目库及题目复用相关接口

第二阶段通过 `app/routes/question_library.py` 中的 `question_library_bp` 组织题目库相关 API，蓝图前缀为：

```text
/api/question-library
```

该模块承担题目库及相关题目复用业务，功能范围对应常用题目保存和复用、题目分享、题目版本与历史管理、题目使用情况查询及题目库管理等需求。具体每个操作的 HTTP 方法、完整子路径、请求体和响应字段，应以当前 `app/routes/question_library.py` 实际注册的路由及业务逻辑为准。

编写或维护 API 文档时，每个具体接口记录了以下信息：请求方法、完整路径、登录和资源权限要求、请求参数、成功响应、可能的错误状态码，以及对数据库的影响。这样可以让 API 文档与代码保持一致。

## 六、关键逻辑说明

### 6.1 逻辑题目标识与问卷题目标识

第一阶段的题目通常通过所属问卷和题目标识进行查询。题目复用以后，同一个逻辑题目可能出现在多个问卷中，因此需要用 `question_key` 之类的逻辑标识识别共同题目，同时仍保留每份问卷内题目实例的关联信息。

逻辑题目标识主要服务于跨问卷定位和统计；问卷内的题目标识用于在提交答案时确定具体题目。统计时不应简单把不同题目的显示文本视为同一题，因为不同题目可能恰好具有相同标题；也不应把不同版本内容混为一个具体版本。应依据系统设计的逻辑标识和版本关联来判断。

### 6.2 题目复用与题目库

题目复用的基本流程是保存可复用题目、在创建新问卷时检索题目、选定题目并加入目标问卷。题目库用于集中组织和管理可复用题目，并为后续创建新问卷提供选题入口。

在这一流程中，后端需要检查当前用户是否有权查看或使用目标题目，并确保目标问卷属于当前用户且处于允许编辑的状态。题库记录与问卷中的题目实例承担不同用途，题库中的更新不应自动改变已发布问卷的历史内容。

### 6.3 题目分享与访问权限

分享题目时，需要区分题目创建者、分享对象及其他未获授权的用户。分享对象可以按系统允许的权限查看或使用被分享题目；分享者仍可继续使用自己的题目。后端应对分享和使用操作执行权限检查，避免用户仅通过猜测或提交其他用户的题目标识来访问受限资源。

### 6.4 版本历史、恢复与版本共存

题目内容需要修改时，版本机制负责保存修改前后的差异或版本记录，并为版本查询和恢复提供依据。版本历史应能说明不同版本之间的关系；恢复旧版本后，系统仍需要按照实际设计保留版本记录。

版本共存意味着旧版本和新版本能够同时被识别和选择。不同问卷可以根据需要使用不同版本，防止一次修改传播到所有使用中的问卷。版本恢复与创建新版本是两个不同概念：恢复操作的业务效果应由当前代码决定，不应在文档中假设恢复一定采用某种内部实现。

### 6.5 已发布问卷内容保护

第一阶段题目管理已限制已发布问卷中的题目修改。第二阶段在题目共享和复用的场景下，需要进一步保证题目库或逻辑题目的后续更新不会意外改变已经发布问卷的题目内容。

设计上可以通过保存问卷使用时的题目快照，或将问卷绑定到明确的题目版本来达到这一目标。无论采用哪种实现，关键结果都应是：修改可复用题目后，旧问卷仍保留原来的题目内容，新的问卷可以在需要时使用新版本。

### 6.6 题目使用情况查询

题目使用情况功能通过题目与问卷之间的关联查询，返回哪些问卷使用了某个题目或题目版本。它帮助用户在修改题目前了解影响范围，也可为是否创建新版本提供依据。

查询结果应受权限范围约束；如果同一逻辑题目在多个问卷中被使用，系统应按其真实关联关系返回信息，而不是仅根据题目标题做字符串匹配。

### 6.7 跨问卷单题统计

跨问卷单题统计的主要逻辑如下：

```text
接收 question_key
        |
        v
确定当前用户可统计的问卷范围
        |
        v
查找这些问卷中使用该逻辑题目的答卷
        |
        v
根据题型整理有效答案
        |
        v
计算答卷数量及题型统计值
        |
        v
返回 JSON 统计结果
```

单份问卷统计与跨问卷单题统计的主要区别在于统计范围：前者以 `survey_id` 为范围，后者以逻辑题目标识为入口，但仍需限定在当前用户有权访问的数据内。

对于数字题，统计时需要区分答卷数量与可用于数字计算的答案数量。空答案不应被误计为有效数字；平均值应基于有效数字答案计算。对于单选或多选题，应按照实际选项标识和答案列表统计选择次数。跨问卷汇总时，使用的逻辑题目应确实对应同一题目，而不能仅因为题目名称相同就自动合并。

### 6.8 与第一阶段功能的兼容

第二阶段的题目复用、分享、版本管理和跨问卷统计依赖第一阶段已有的问卷、题目和答卷流程，因此继续保留以下行为：

- 用户能够注册和登录，并以当前用户身份管理自己的问卷。
- 问卷能够创建、编辑、发布、关闭和通过分享码访问。
- 题目仍支持单选、多选、文本和数字等第一阶段题型。
- 后端继续执行题目配置、答案有效性和条件跳转路径校验。
- 答卷成功提交后仍按原流程保存，问卷统计继续基于已保存的答卷记录计算。
- 新增题目版本和逻辑题目标识不应破坏旧问卷中题目与答案之间的对应关系。

## 八、运行和维护注意事项

1. **确认数据库配置。** 启动应用或运行测试前，核对 `MONGO_URI` 和 `MONGO_DB_NAME`，避免把测试数据写入开发数据库。
2. **保持接口文档与代码一致。** 题目库相关接口的完整方法、路径、参数和响应字段应从 `app/routes/question_library.py` 的实际路由定义更新到本文件。

4. **检查统计权限。** 跨问卷统计应限定在当前用户有权查看的数据范围内，不能仅按题目标识查询所有用户的数据。
