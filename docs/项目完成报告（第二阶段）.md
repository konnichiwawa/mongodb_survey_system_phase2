# 基于 MongoDB 的问卷系统开发——第二阶段项目完成报告

## 项目概述

本项目是“当代数据管理系统”课程大作业的第二阶段。第一阶段已经实现基于 Python、Flask 和 MongoDB 的问卷系统核心流程，包括用户注册与登录、问卷创建与管理、题目配置、问卷发布与分享访问、答卷提交、答案校验、条件跳转和问卷统计等功能。

第二阶段没有另起一套系统，而是在第一阶段项目结构和业务流程的基础上，根据需求变更说明扩展题目资源管理和统计能力。本阶段的八项需求分别是：保存常用题目并复用、分享题目、修改题目时保护已完成问卷、记录题目修改历史、允许同一题目的多个版本共存、查询题目被哪些问卷使用、建立题库，以及查看单个逻辑题目跨问卷的统计结果。

本报告重点记录原有设计、新需求带来的问题、设计调整原因、数据与程序的变化、兼容性处理、旧功能保障、MongoDB 设计取舍，以及 AI 辅助开发的实际使用过程。

# 一、项目目标

## 1.1 项目背景与目标

本项目是“当代数据管理系统”课程大作业的第二阶段。在第一阶段实现基于 MongoDB 的问卷系统后，本阶段继续在原有项目的基础上进行功能扩展和改进，而不是重新开发一套独立系统。

第一阶段系统已经具备用户注册与登录、问卷创建与管理、题目配置、问卷发布与分享、答卷提交、答案校验、条件跳转和统计查询等基本功能。随着题目重复使用和问卷长期维护的需求增加，原有以单份问卷和具体题目为中心的管理方式需要进一步扩展。

因此，第二阶段的主要目标是完善题目资源的管理能力，使题目不再局限于单份问卷中使用，同时支持题目复用、分享、版本管理、题目使用情况查询、题库管理和跨问卷单题统计等功能。

本阶段的具体目标如下：

1. **实现常用题目的保存与复用。** 用户可以保存常用题目，并在创建新问卷时再次使用，减少重复创建相同题目的工作。
2. **支持题目分享。** 允许用户将题目分享给其他用户，使被分享的用户能够按照系统规定的权限使用题目。
3. **保护已经发布的问卷内容。** 修改题目时，应避免意外改变已经完成或发布的问卷中的题目内容，保证历史问卷与已有答卷之间的一致性。
4. **支持题目修改历史与版本恢复。** 记录题目修改过程中形成的版本信息，使用户能够查询历史版本，并根据系统支持的规则恢复旧版本。
5. **支持同一逻辑题目的多个版本共存。** 允许题目基于原有版本继续修改，不同问卷可以根据需要使用不同版本，而不必强制同步到同一份当前内容。
6. **支持查询题目使用情况。** 用户能够查看某个题目被哪些问卷使用，为后续修改和版本选择提供参考。
7. **建立题库管理能力。** 将常用题目集中管理，使用户可以向题库添加题目，并在创建问卷时从题库中选题。
8. **支持跨问卷单题统计。** 在符合用户权限的范围内，汇总同一逻辑题目在不同问卷中的回答情况，扩展原有以单份问卷为统计范围的功能。

## 1.2 项目实施目标

在实现上述功能的同时，本阶段还需要满足以下实施目标。

首先，保留第一阶段的核心架构和主要业务功能，尽量通过在原有代码上增加或调整模块完成需求扩展，避免不必要的整体重构。

其次，根据新增需求调整数据组织和业务关联方式，使系统能够表达逻辑题目、题目版本、题目与问卷之间的关系，并为跨问卷统计提供数据基础。

再次，继续使用 Flask 提供后端 API，使用 MongoDB 保存业务数据。题目内容、校验配置和跳转规则等可变化的信息应由数据进行描述，后端负责统一执行相应的业务规则，避免针对每份问卷将具体内容写死在代码中。

最后，通过自动化测试验证程序调整后的主要行为，并检查原有测试是否仍然通过，以降低新增功能对已有功能造成影响的风险。

# 二、系统设计

## 2.1 系统总体架构

本项目继续采用 Python、Flask 和 MongoDB 构建问卷系统。Flask 负责接收和处理 HTTP API 请求，MongoDB 负责保存用户、问卷、题目和答卷等业务数据，后端路由模块负责执行权限判断、输入校验、题目版本相关操作和统计计算。

第二阶段沿用第一阶段的总体架构，并根据新增需求扩展题目库和相关统计处理逻辑。系统的整体结构可以概括为：

```text
用户 / HTTP API 请求
        |
        v
Flask 应用
        |
        +---- 用户认证模块
        |
        +---- 问卷管理模块
        |
        +---- 题目管理模块
        |
        +---- 题目库及题目复用模块
        |
        +---- 答卷提交与校验模块
        |
        +---- 问卷统计与单题统计模块
        |
        v
MongoDB 数据库
        |
        +---- users
        +---- surveys
        +---- questions
        +---- responses
        +---- 题目复用及版本管理相关数据
```

以上结构用于说明系统的业务模块和数据访问关系。题目库、版本和分享相关信息的具体物理存储方式，以项目实际代码为准，不代表每一类业务信息都对应一个独立集合。

## 2.2 系统模块划分

本阶段继续按照业务职责划分系统模块，主要模块及其作用如下。

| 模块 | 主要职责 |
|---|---|
| 用户认证模块 | 负责用户注册、登录、退出登录及当前用户状态查询 |
| 问卷管理模块 | 负责问卷创建、查询、发布、关闭、截止时间设置和分享访问 |
| 题目管理模块 | 负责问卷题目的创建、查询、修改、删除及题目配置校验 |
| 题目库与复用模块 | 支持常用题目保存、题目复用、题库管理以及相关分享和版本管理操作 |
| 答卷提交模块 | 检查问卷状态、答案格式、题目归属和条件跳转路径，并保存合法答卷 |
| 问卷统计模块 | 根据问卷标识查询答卷并汇总题目统计结果 |
| 跨问卷单题统计模块 | 根据逻辑题目标识，在授权的数据范围内聚合不同问卷中的相关回答 |

其中，题目管理模块主要处理问卷中的具体题目，题目库与复用模块则面向可重复使用的题目资源。两者相互关联，但职责并不相同。

## 2.3 主要业务流程设计

第二阶段在保留原有问卷业务流程的基础上，增加了题目资源管理流程。

**（1）原有问卷流程**

用户注册并登录后，可以创建问卷、添加题目和配置题目规则。问卷满足发布条件后，可以发布并通过分享码访问。填写者提交答案后，系统执行答案校验和条件跳转校验，验证通过后将答卷保存到 MongoDB。问卷创建者可以查询该问卷的统计结果。

**（2）题目复用与题库流程**

用户将常用题目保存到可复用的题目资源中，之后创建新问卷时可以查找并选用已有题目。题目资源的管理与问卷中实际使用的题目需要保持合理的关联，避免题库中的后续修改意外改变已发布问卷的内容。

**（3）题目分享与版本管理流程**

用户根据系统支持的规则分享题目，其他用户按照获得的权限查看或使用相应资源。题目修改时，需要结合版本管理和问卷使用情况决定如何保存新内容，并保留必要的历史信息，以便追溯修改来源或恢复旧版本。

**（4）跨问卷单题统计流程**

用户请求某一逻辑题目的统计结果后，后端根据逻辑题目标识查找相关数据，在当前用户有权统计的范围内汇总不同问卷中的回答，并根据题目类型计算相应结果。

## 2.4 系统设计原则

为了满足第二阶段的需求，同时尽量减少对第一阶段功能的影响，本项目采用以下设计原则。

**第一，保留原有核心结构。** 在第一阶段 Flask 应用、路由模块和 MongoDB 数据组织方式的基础上继续开发，优先扩展已有模块或增加必要的处理逻辑，避免无关的整体重构。

**第二，按业务职责组织数据。** 用户、问卷、题目和答卷分别承担不同职责。题目复用、版本和分享等新需求应当通过清晰的业务关联实现，而不是将所有数据合并到单个集合中。

**第三，区分逻辑题目和具体题目版本。** 逻辑题目标识用于识别同一逻辑题目，具体题目标识用于定位相应记录。通过明确两者的作用，为题目复用、版本共存和跨问卷统计提供基础。

**第四，将变化的业务配置作为数据保存。** 题目标题、选项、校验条件和跳转规则由数据库中的题目配置进行描述，后端执行统一的校验和处理逻辑，避免将具体问卷内容写死在代码中。

**第五，由后端检查权限和数据合法性。** 对题目分享、题库管理、问卷管理和跨问卷统计等操作，不能仅依据请求中提供的标识执行操作，还需要检查用户身份、资源关联和访问权限。

**第六，通过自动化测试检查兼容性。** 在扩展新功能时继续运行原有测试，并为新增功能增加相应测试，检查代码调整是否影响已有业务流程。

综上，第二阶段的系统设计是在第一阶段架构基础上进行扩展：一方面保留已有的问卷创建、题目管理、提交和统计流程；另一方面增加题目资源复用、版本关联和跨问卷统计所需的业务能力。通过模块职责划分、MongoDB 数据模型调整、后端规则处理和自动化测试，系统能够在原有功能基础上逐步适应新的需求。

## 三、MongoDB 设计要求

## 3.1 第一阶段数据库设计基础

第一阶段采用 MongoDB 保存问卷系统的数据，核心集合包括 `users`、`surveys`、`questions` 和 `responses`。

| 集合 | 主要职责 |
|---|---|
| `users` | 保存用户账号及认证信息 |
| `surveys` | 保存问卷标题、创建者、状态、分享码等基本信息 |
| `questions` | 保存问卷中的题目、题型、选项、校验规则和跳转配置 |
| `responses` | 保存答卷所属问卷、答案列表和提交时间等信息 |

第一阶段将不同业务对象分开存储，通过 `survey_id` 等业务标识建立问卷、题目和答卷之间的关联。题目的选项、校验配置和跳转规则与题目联系紧密，因此可以作为题目文档中的嵌入式数据；一次答卷中的多个答案则可以保存在该答卷的 `answers` 数组中。

这种设计能够区分不同业务对象的职责，也避免将不断增长的答卷数据全部放在问卷文档中，为第二阶段的扩展保留了基础。

## 为什么这样设计

## 3.2.1第二阶段的核心变化：从问卷内题目到可复用题目

第二阶段的八项需求主要围绕题目的重复使用、分享、版本管理和统计展开。第一阶段主要通过具体题目标识和问卷标识管理题目，第二阶段则需要进一步表达：**不同问卷中的题目是否属于同一道逻辑题目，以及它们使用的是哪个版本。**

例如，用户希望在多个问卷中重复使用“你的年龄”这一题目。不同问卷可能使用相同的题目内容，也可能分别使用修改前后的版本。如果仅依靠某份问卷内的题目标识，就难以直接识别不同问卷中的题目之间的逻辑联系。

因此，第二阶段需要强化以下数据概念：

| 数据概念 | 主要作用 | 对应需求 |
|---|---|---|
| 逻辑题目标识 `question_key` | 识别属于同一逻辑题目的相关题目和回答 | 题目复用、题目使用情况查询、跨问卷统计 |
| 题目版本 | 区分同一逻辑题目在不同阶段形成的内容 | 修改保护、历史记录、版本共存及恢复 |
| 题目与问卷的关联 | 记录题目在哪份问卷中使用 | 查询题目被哪些问卷使用 |
| 题目所有权与分享关系 | 判断谁拥有题目，以及其他用户能进行哪些操作 | 题目分享 |
| 题库与题目的关联 | 支持题目保存、管理和再次选用 | 题库管理与常用题目复用 |


## 3.2.2 题目复用与版本管理的数据设计

第二阶段的需求三、需求四和需求五对数据设计提出了一个关键要求：题目发生修改时，不能简单地覆盖所有问卷正在使用的内容。

例如，问卷 A 使用题目版本 v1，用户随后修改题目形成版本 v2，并希望问卷 B 使用新版题目。如果系统始终让所有问卷读取同一份不断变化的题目内容，那么修改 v2 时就可能影响问卷 A 的原有内容。

因此，数据库设计需要从逻辑上区分三个层次：

1. **逻辑题目**：表示可重复使用的题目概念，例如“你的年龄”。
2. **题目版本**：表示该逻辑题目在某一阶段的具体内容和配置。
3. **问卷实际使用的题目内容**：表示某份问卷在创建或发布时采用的题目内容和规则。

题目复用解决的是重复创建的问题，版本管理解决的是内容变化和历史追溯的问题，问卷实际使用内容的保护则用于避免后续修改破坏已发布问卷。

在实现时，通过逻辑题目标识、版本关联信息及问卷题目数据组织这些关系。题目被修改时，应根据系统的版本规则创建或使用新版本，而不是无条件覆盖旧版本；恢复旧版本时，也应保留必要的历史记录，便于追踪修改过程。

## 3.2.3 题目分享、题库和使用情况查询

第二阶段的需求二、需求六和需求七进一步扩展了题目资源的管理方式。

**题目分享**要求系统能够区分题目的所有者与获得使用权限的其他用户。用户分享题目后，其他用户可以在自己的问卷中使用该题，但获得使用权不应自动等同于获得原题目的修改权或删除权。因此，相关业务需要维护必要的所有权和分享权限信息，并由后端执行访问检查。

**题库管理**要求常用题目不再局限于某一份问卷。用户可以将题目保存到题库，在创建新问卷时查找并选用已有题目。题库数据与问卷实际使用的题目承担不同职责：题库用于管理可复用的题目资源，问卷中的题目用于实际答题和答案校验。题库更新也不应在没有版本规则的情况下改变已经发布的问卷。

**题目使用情况查询**要求系统能够判断某个逻辑题目被哪些问卷使用。这样，用户在修改题目之前可以了解其使用范围，并根据实际情况决定是否创建新版本。

## 3.2.4 跨问卷单题统计的数据设计

第二阶段的需求八是查看同一道逻辑题目在不同问卷中的回答情况。第一阶段的问卷统计主要针对一份问卷，而跨问卷统计需要进一步识别分散在不同问卷中的同一逻辑题目。

为此，项目新增了后端接口：

`GET /api/responses/question-stats/<question_key>`

该接口使用 `question_key` 定位逻辑题目，并汇总当前用户创建的、符合统计范围的问卷中与该逻辑题目相关的答卷数据。统计过程中仍需要遵守用户权限，不能把其他用户无权查看的数据直接纳入结果。

跨问卷统计需要区分以下几个概念：

| 统计内容 | 说明 |
|---|---|
| 答卷数量 | 符合统计条件的答卷记录数量 |
| 有效数字答案数量 | 实际参与数字统计的答案数量 |
| 选项选择次数 | 某个选项被选择的次数 |
| 文本答案 | 符合统计范围的文本回答 |

不同统计指标的数量可能不同。例如，一份多选题答卷可以选择多个选项，因此各选项的选择次数之和可能大于答卷总数；数字题存在空答案时，参与平均值计算的答案数量也可能小于答卷总数。

与第一阶段相比，这项功能的关键变化不是简单增加一种统计结果，而是需要通过逻辑题目标识，将题目关联、问卷范围、答卷数据和统计计算连接起来。

目前已确认该接口的相关筛选测试为 `4 passed, 36 deselected`，完整自动化测试为 `40 passed`。这些结果证明对应测试成功运行，但不能据此认为所有统计边界情况均已覆盖。

## 3.3 为什么不把所有数据放在一个集合中

第二阶段增加了题目复用、版本、分享、题库和跨问卷统计等需求。如果将用户、问卷、题目、历史版本和全部答卷都存储在同一个大型文档中，数据结构会越来越复杂，部分查询也可能需要读取大量无关内容。

同时，不同数据的生命周期和增长方式不同：用户数据相对稳定，问卷有独立的发布状态，题目可能产生多个版本，答卷则会随提交持续增加。将它们全部放在一起，会增加更新和维护的复杂度，也更容易使不同业务相互影响。

因此，本项目继续采用按业务对象组织数据的方式，在保留第一阶段核心集合的基础上扩展第二阶段需要表达的题目关联关系，而不是把全部业务集中在一个集合中。

## 3.4 为什么不把每项配置都拆成独立集合

MongoDB 支持嵌入式文档和数组，适合保存与主体联系紧密、通常需要一起读取的配置。

例如，题目的选项、校验规则和跳转规则通常需要与题目一起读取；一次答卷中的多个答案共同构成完整提交。这些数据可以根据实际结构嵌入相应文档中。

如果把每个选项、每条校验规则和每个答案都拆成独立集合，查询完整题目或一次答卷时就需要额外读取和组装数据，增加不必要的关联和维护成本。

因此，本项目的设计思路是：具有独立生命周期或需要独立查询维护的数据采用独立文档组织；与所属对象联系紧密、通常需要一起读取的数据则考虑嵌入。数据组织方式应服务于业务需求，而不是单纯追求集合数量多或少。

## 3.5 数据冗余、索引与完整性约束

题目复用和版本管理需要在数据独立性与冗余之间进行权衡。

如果所有问卷都直接读取同一份可修改的题目数据，更新时可能影响历史问卷；如果在每个位置无条件复制全部题目内容，又会增加数据重复和维护成本。因此，需要明确可复用题目、具体版本和问卷实际使用内容之间的关系，并通过必要的标识建立关联。

第一阶段已有索引包括用户名唯一索引、问卷分享码唯一索引、按创建者和创建时间查询问卷的组合索引、同一问卷内题目顺序的唯一索引，以及按问卷和提交时间查询答卷的索引等。

第二阶段增加了按逻辑题目标识查询、查找题目使用关系和跨问卷统计等场景。但是否为新增字段建立索引，需要根据当前 `app/init_db.py` 中的真实索引定义和实际查询方式判断，不能因为某个字段参与查询，就直接宣称该字段已经建立索引。

此外，MongoDB 的业务标识关联不能代替应用层的完整性检查。例如，文档中存在 `survey_id` 不代表对应问卷一定存在；题目和答卷之间具有标识关联，也不代表当前用户一定有权限访问。系统仍需要由后端检查数据归属、访问权限、题目关联关系和提交条件。

## 3.6 为什么不用关系数据库结构

关系型数据库同样能够实现本问卷系统。用户、问卷、题目和答卷可以分别设计为数据表，并通过主键、外键和关联查询维护它们之间的关系。因此，本项目不选择关系型数据库，并不是因为关系型数据库无法满足需求，而是因为 MongoDB 的文档模型更符合本项目的题目配置特点和第二阶段的扩展方向。

**第一，不同题型的配置存在差异。** 本系统支持单选题、多选题、文本题和数字题，不同题型需要保存的配置并不完全相同。例如，选择题需要选项列表，文本题需要长度限制，数字题需要数值范围，部分题目还需要保存条件跳转规则。采用 MongoDB，可以通过文档、数组和嵌入式字段组织这些配置，不必为了每种题型都设计额外的配置表。当然，关系型数据库也可以通过关联表或 JSON 字段实现相同需求，但对于当前项目而言，MongoDB 的文档结构比较直观。

**第二，题目与其配置具有较强的关联性。** 选项、校验规则和跳转规则通常需要与题目一起读取和使用。将这些内容保存在题目文档中，可以减少读取完整题目时的额外查询和数据组装工作。与此同时，用户、问卷、题目和答卷仍然按照业务职责分别组织，避免为了追求灵活性而将所有数据放在一个集合中。

**第三，第二阶段需要支持题目复用和版本管理。** 同一逻辑题目可能被多个问卷使用，也可能存在多个不同版本。MongoDB 可以通过文档及业务标识组织这些关联关系，并根据实际需求保存题目内容和版本信息。不过，MongoDB 本身不会自动解决版本管理问题，仍需要由后端程序维护题目版本、问卷使用内容和相关权限。

**第四，MongoDB 符合本课程的设计目标。** 本项目要求使用 MongoDB 完成问卷系统的设计与扩展。通过本次开发，可以实践文档建模、嵌入式数据组织、业务标识关联和索引设计，并理解如何由应用程序维护数据一致性。

综合来看，本项目选择 MongoDB，主要是因为其文档模型适合保存具有差异化配置的题目数据，也能满足第二阶段题目复用、版本管理和跨问卷统计的设计需求。

## 3.7 为什么适合 MongoDB

关系型数据库同样能够实现本系统。用户、问卷、题目和答卷之间的关联可以通过表、主键、外键和关联查询表达。因此，本项目选择 MongoDB，并不是认为关系型数据库无法完成这些需求，而是考虑了以下因素。

第一，不同题型的配置存在明显差异。单选题和多选题需要选项列表，文本题需要长度限制，数字题需要数值范围，题目还可能包含跳转规则。MongoDB 的文档结构能够灵活表达这些差异化配置。

第二，选项、校验规则和跳转规则与题目联系紧密，嵌入式文档能够方便地将相关数据组织在一起。

第三，第二阶段需要进一步关联逻辑题目、版本和多个问卷中的答卷。MongoDB 可以保存相应的业务标识，并结合后端查询和统计逻辑处理这些关系。

第四，MongoDB 支持唯一索引和组合索引，可以配合用户查找、问卷管理、分享码访问和答卷查询等场景。

## 4.2 AI 使用说明

### 4.2.1 AI 帮助了什么

**第一，帮助拆解八项需求。**

第二阶段的需求之间存在较强联系。例如，常用题目复用需要题目资源能够脱离单份问卷被再次使用；题目版本管理需要区分逻辑题目和具体版本；题目使用情况查询需要建立题目与问卷之间可追踪的关联；跨问卷统计则需要按逻辑题目标识定位相关回答。

AI 协助把这些联系整理为独立的需求任务，使数据库设计、程序修改和测试用例能够围绕明确的目标展开。

**第二，帮助理解 MongoDB 的数据建模取舍。**

AI 协助解释了为什么继续保留 `users`、`surveys`、`questions` 和 `responses` 的业务职责划分，以及选项、校验规则和跳转规则为什么可以考虑使用嵌入式文档。

对于第二阶段，AI 进一步协助分析逻辑题目标识、版本管理、题目复用和跨问卷统计需要表达的数据关系，使报告不只介绍集合名称，还能够说明设计理由和适用边界。

**第三，协助实现和排查跨问卷单题统计。**

AI 参与修改 `app/routes/responses.py`，协助实现跨问卷单题统计接口，并围绕 `question_key` 设计相关测试。

在测试过程中，统计结果的 JSON 层级需要与断言保持一致。通过检查实际返回结构、调整断言以及运行筛选测试，最终得到四项相关测试通过的结果。

**第四，帮助检查代码和测试。**

AI 协助检查 `app/routes/question_library.py` 和 `app/routes/responses.py` 的 Python 语法，并整理测试命令和输出结果。这有助于在修改文件后尽早发现语法层面的问题。

不过，语法检查只能证明代码能够通过语法解析，不能单独证明接口行为、权限控制或业务逻辑完全正确。因此，还需要结合自动化测试验证实际行为。

### 4.2.2 AI 做错了什么，以及存在的局限

AI 的代码和文档建议并非每次都能直接使用。本阶段出现的问题包括以下几类。

**第一，题目库路由文件曾被错误覆盖。**

开发过程中，`app/routes/question_library.py` 曾被错误覆盖，导致需要根据用户提供的原始代码进行恢复。

这说明 AI 在处理较长的源文件时，可能误删或覆盖原有内容。后续不能只检查新文件是否存在或是否能够通过语法解析，还应对照原始版本检查已有蓝图、路由和业务逻辑是否保留。

**第二，测试断言需要根据实际响应进行修正。**

跨问卷单题统计接口的返回结果具有嵌套结构，统计对象位于 JSON 的 `stats` 字段内。如果测试代码直接从错误的数据层级读取统计结果，就可能出现断言错误。

本阶段根据实际响应调整了统计对象和数字统计字段的读取方式，之后单题统计筛选测试全部通过。这说明 AI 生成的测试代码仍需要根据接口真实响应核对，不能只检查代码能否运行。

**第三，通用的数据库设计建议不一定等同于实际项目实现。**

AI 可以提出逻辑题目、题目版本、分享关系和题库等数据建模思路，但这些概念不一定分别对应独立的 MongoDB 集合，也不代表具体字段已经存在于当前源码中。

因此，在整理数据库文档时，需要将业务概念与物理数据结构区分开来。未经源码核对的字段名称、集合名称和索引不能直接描述为已实现内容。

**第四，整体测试通过不能代替每一项需求的独立验证。**

本阶段最近一次完整自动化测试结果为四十项通过，单独运行单题统计相关测试时为四项通过。但完整测试通过不能直接说明八项需求的所有业务分支都分别完成了测试。

因此，报告需要区分完整回归测试结果、与特定接口有关的筛选测试结果，以及尚无独立测试日志支持的场景。对于没有实际响应或日志的场景，不能直接由具体测试输出。

### 4.2.4 自己设计和确认了什么

本阶段的开发不只是将 AI 生成的代码直接加入项目。根据实验要求和需求变更说明，我参与了以下设计取舍与确认。

**第一，确定在第一阶段基础上扩展，而不是推倒重做。**

项目继续使用第一阶段的 Flask、MongoDB 和既有问卷业务结构。第二阶段围绕新增需求修改相关模块，并保留原有问卷创建、题目配置、答卷提交和统计功能。

这一原则减少了无关的整体重构，也使新需求能够与现有系统共同工作。

**第二，明确八项需求之间的对应关系。**

测试用例按需求变更中的任务一至任务八重新编号，确保常用题目复用、题目分享、已发布问卷保护、修改历史、版本共存、使用情况查询、题库管理和跨问卷统计分别得到说明。

**第三，明确跨问卷统计以逻辑题目标识为依据。**

第二阶段增加了 `GET /api/responses/question-stats/<question_key>` 接口。与单份问卷统计相比，这项功能需要把同一逻辑题目在不同问卷中的使用场景关联起来，并在相应权限范围内汇总回答。

同时，具体题目标识与逻辑题目标识承担不同的用途，因此不能仅根据题目标题相同，就直接认定它们属于同一个逻辑题目。

**第四，强调题目复用与历史内容保护之间的关系。**

题目能够复用，并不意味着所有问卷都应该始终读取同一份不断变化的内容。题目版本需要能够区分不同阶段形成的内容，已发布问卷则应避免受到后续题目更新的意外影响。

报告因此分别讨论题目复用、版本管理和问卷实际使用内容，而不是将这些问题简单等同于复制题目。

**第五，坚持数据与业务逻辑分工。**

题目标题、选项、校验配置和跳转规则属于会随问卷变化的数据；后端则负责执行统一的权限检查、输入校验和业务规则。

通过这种分工，系统不需要针对每份问卷把具体题目和规则写死在 Python 代码中，同时仍然保留后端对请求合法性和数据权限的控制。

**第六，以实际测试记录作为功能验证依据。**

本阶段采用 `python -m pytest` 执行自动化测试。已确认的完整测试结果为四十项全部通过，单题统计筛选测试为四项通过。我根据实际输出记录测试结果，同时区分完整回归测试与独立功能验证，不将没有证据支持的场景写成已经单独测试成功。

### 4.2.5 AI 辅助开发的总结

经过本阶段开发，可以看出 AI 的价值主要在于加快需求分析、提供代码实现思路、协助检查业务逻辑、调整测试和整理文档。但 AI 输出仍然可能出现文件覆盖、断言错误、细节推断和文档结构不符合要求等问题。

因此，本项目采用的实际工作方式并不是直接接受所有 AI 输出，而是结合需求文档、源代码、测试命令和运行结果持续核对。在出现错误时恢复原始代码并重新检查；在测试断言与实际接口响应不一致时调整测试；在文档内容不符合课程要求时，根据实际需求重新组织。

## 五、第一阶段的设计是什么

第一阶段的目标是开发一套基于 MongoDB 的简化在线问卷系统。系统使用 Python 作为后端开发语言，以 Flask 提供 HTTP API，并通过 PyMongo 访问 MongoDB。项目使用 `run.py` 作为应用启动入口，`app/__init__.py` 负责创建 Flask 应用和注册路由，`app/db.py` 负责数据库连接，`app/init_db.py` 负责初始化数据库所需的集合和索引。

第一阶段的系统设计以问卷的完整业务流程为中心，主要功能包括：

1. **用户认证：** 支持用户注册、登录、退出登录和当前登录状态查询。
2. **问卷管理：** 支持创建问卷、查询本人创建的问卷、发布问卷、关闭问卷以及设置截止时间。
3. **题目管理：** 支持向问卷添加题目、查询题目、修改题目和删除题目。
4. **题型与数据校验：** 支持单选题、多选题、文本题和数字题，并根据不同题型执行相应的题目配置与答案校验。
5. **条件跳转：** 支持部分题型根据答案决定后续答题路径，并在提交答卷时校验答案是否符合实际答题路径。
6. **答卷提交：** 用户可以通过分享码访问已发布问卷，填写答案并提交，系统负责校验并保存答卷。
7. **统计查询：** 问卷创建者可以查询自己问卷的统计结果，包括选择题选项计数、文本回答以及数字答案的相关统计。

第一阶段的数据库主要采用 `users`、`surveys`、`questions` 和 `responses` 四个核心集合。其中，用户信息单独保存；问卷集合保存问卷基本信息、创建者、状态和分享码等数据；题目集合保存题目内容、题型、选项、校验规则和跳转配置；答卷集合保存问卷关联信息、答案列表及提交时间。

题目通过 `survey_id` 与所属问卷建立关联，答卷也通过 `survey_id` 与对应问卷建立关联。选项、校验规则和跳转规则与题目关系紧密，因此可以保存在题目文档中；一次答卷中的多个答案共同构成一份提交记录，可以保存在该答卷文档的 `answers` 数组中。

这种设计满足了问卷从创建、配置、发布、填写、提交到统计的基本流程，也为第二阶段继续扩展功能提供了基础。

但第一阶段主要将题目看作某份问卷中的具体对象，统计范围也主要是一份问卷。对于题目如何被多份问卷复用、不同用户如何共享题目、题目如何形成多个版本，以及如何统计同一逻辑题目在不同问卷中的回答情况，原有的数据模型和业务流程还需要进一步扩展。

## 六、新需求带来了哪些问题

第二阶段的需求变更包含八项任务。这些需求不仅要求增加新的操作，还改变了系统对题目的管理方式：题目需要能够独立保存和复用，并进一步支持分享、版本管理、使用关系查询和跨问卷统计。

### 6.1 任务一：保存常用题目并重复使用

第一阶段主要围绕某份问卷创建和管理题目。用户需要在不同问卷中使用相同题目时，如果每次都重新创建，就会产生重复工作，也不利于统一维护常用题目。

新需求要求系统能够保存常用题目，并在创建新问卷时再次选用。因此，题目不能只被理解为某份问卷内部的数据，还需要具备可被再次使用的资源属性。

### 6.2 任务二：将题目分享给其他用户

题目分享涉及题目所有者、被分享用户和未授权用户之间的权限区别。

如果系统只保存题目内容，却没有清晰的分享关系和权限判断，就难以确定其他用户能否查看、复用或修改题目。因此，新增需求要求在题目复用的基础上考虑资源所有权和访问权限，避免将题目使用权直接等同于所有权。

### 6.3 任务三：修改题目时保护已完成的问卷

如果多个问卷都直接依赖一份可以随时修改的公共题目，修改题目标题、选项或校验条件时，就可能改变已经发布的问卷内容。

这会导致历史问卷与当时收集的答卷之间出现不一致。例如，问卷发布时使用旧选项，之后题库更新了选项，如果旧问卷也同步变化，原有答卷就可能难以按照原先的题目定义进行解释。

因此，系统需要明确题目更新与问卷历史内容之间的边界，避免后续修改无条件影响已有问卷。

### 6.4 任务四：记录题目修改历史

如果题目每次修改都直接覆盖原有内容，就无法完整查看题目从旧版本到新版本的变化，也难以找回先前的版本。

新需求要求系统能够查看题目历史版本、了解新版本的来源，并在需要时恢复旧版本。这意味着数据结构和程序需要能够表达版本之间的关系，而不能只保存一份当前题目内容。

### 6.5 任务五：同一题目的不同版本同时存在

实际使用中，同一逻辑题目可能根据不同问卷的需要进行调整。例如，一份问卷使用原来的题目，另一份问卷使用修改后的版本。

如果系统只允许同一逻辑题目存在一个当前内容，就难以让不同问卷分别使用不同版本。因此，需要区分逻辑题目与具体版本，使题目更新不会强制覆盖所有使用场景。

### 6.6 任务六：查询题目被哪些问卷使用

用户在修改题目前，希望知道该题目是否正在被其他问卷使用。如果系统不能追踪题目与问卷之间的关系，就难以判断修改可能影响的范围。

因此，系统需要能够根据题目标识或相关关联信息查询题目的使用情况，为版本选择和修改决策提供依据。

### 6.7 任务七：建立题库

题库要求将常用题目集中组织起来，使用户可以保存、查询、管理并再次选用题目。

题库资源与问卷实际使用的题目承担不同职责。如果没有明确区分，题库中的内容更新就可能影响已经发布的问卷。因此，题库不仅涉及题目的保存和查询，还需要与题目复用、版本管理和问卷内容保护相互配合。

### 6.8 任务八：查看单个题目的跨问卷统计结果

第一阶段的统计功能主要围绕一份问卷开展。如果同一道逻辑题目被使用在多个问卷中，用户无法仅通过单份问卷统计直接了解该题目的总体回答情况。

新需求要求系统能够识别不同问卷中属于同一逻辑题目的题目及回答，再根据统计权限汇总数据。

这需要将逻辑题目标识、具体题目标识、问卷关联信息和答卷数据结合起来，同时区分答卷数量、有效数字答案数量和选项选择次数等不同统计指标。

## 七、为什么需要修改原设计

第一阶段的设计能够支持问卷创建、题目配置、答卷提交和单问卷统计，但其数据组织方式主要面向问卷内部的题目管理。第二阶段要求题目能够跨问卷、跨用户复用，并进一步支持版本管理和跨问卷统计，因此需要在保留原有核心结构的基础上扩展设计。

首先，原有具体题目标识主要用于定位某份问卷中的题目，不能单独承担跨问卷识别同一逻辑题目的全部职责。为了支持题目复用和跨问卷统计，需要引入或强化逻辑题目标识的概念，并明确它与具体题目标识之间的区别。

其次，题目复用增加了数据一致性方面的要求。如果多个问卷都直接依赖同一份可变题目内容，修改公共题目就可能影响旧问卷。因而需要区分可复用题目资源、题目版本和问卷实际使用的题目内容，并明确更新时应遵循的规则。

再次，题目分享与题库管理要求系统明确题目所有权、分享权限和使用关系。用户能够使用一项题目资源，并不代表其自动拥有修改或删除该资源的权限。因此，后端需要根据实际操作检查用户身份、资源归属及授权情况。

最后，原有统计逻辑主要以 `survey_id` 为查询范围，而新增功能以逻辑题目标识为核心，需要从多个符合权限范围的问卷中汇总相关回答。这使统计查询的筛选条件和数据组织方式都需要扩展。

因此，本阶段修改原设计的目标不是替换第一阶段，而是在保留用户认证、问卷管理、题目校验、答卷提交和原有统计流程的基础上，增加题目资源管理所需要的数据关系和业务处理能力。

## 八、修改了哪些部分

第二阶段围绕需求变更说明中的八项任务，对题目资源管理和统计能力进行扩展。

| 任务 | 修改方向 | 主要目标 |
|---|---|---|
| 一、常用题目复用 | 扩展题目资源的保存与选用流程 | 使常用题目能够在不同问卷中重复使用 |
| 二、题目分享 | 扩展题目资源的共享与访问控制 | 使其他用户可以按授权使用题目 |
| 三、保护已发布问卷 | 明确题目更新与旧问卷内容之间的边界 | 避免公共题目修改无条件改变已发布问卷 |
| 四、题目历史与恢复 | 增加对版本历史和来源关系的业务支持 | 支持查询历史版本和恢复旧版本 |
| 五、版本共存 | 区分逻辑题目与具体版本 | 使不同问卷可以使用不同版本的题目 |
| 六、题目使用情况 | 扩展题目与问卷之间的关联查询 | 让用户能够了解题目的使用范围 |
| 七、题库管理 | 扩展可复用题目的管理和选用方式 | 支持题目集中保存、查询和使用 |
| 八、跨问卷单题统计 | 在答卷处理模块中增加单题统计接口 | 按逻辑题目标识汇总相关问卷中的回答 |

在代码模块方面，项目继续沿用原有 Flask 路由结构。题库相关业务由 `app/routes/question_library.py` 所对应的模块承担；新增的跨问卷单题统计处理位于 `app/routes/responses.py` 中。

已经确认新增的统计接口为：

`GET /api/responses/question-stats/<question_key>`

该接口与原有按问卷标识统计的功能承担不同职责：原统计接口围绕单份问卷，新增接口围绕逻辑题目标识，在符合权限要求的范围内汇总相关回答。

测试方面，`tests/test_api.py` 中增加了四项与 `question_stats` 相关的测试，并根据实际接口返回结构调整统计断言。

## 九、数据结构如何变化

第二阶段的数据结构变化可以概括为：保留第一阶段核心集合的业务职责，在原有问卷、题目和答卷关联关系之上，扩展题目复用、版本管理、题目分享和跨问卷统计所需要表达的业务概念。

### 9.1 第一阶段的数据结构

第一阶段核心集合包括：

- `users`：用户账号及认证相关数据。
- `surveys`：问卷基本信息、创建者、状态和分享码等数据。
- `questions`：问卷实际使用的题目、题型、选项、校验配置和跳转规则。
- `responses`：答卷所属问卷、答案列表和提交时间等数据。

其中，题目和答卷通过 `survey_id` 与问卷关联。

### 9.2 第二阶段扩展的数据概念

第二阶段进一步需要表达以下关系：

| 数据概念 | 主要作用 |
|---|---|
| 逻辑题目标识 `question_key` | 识别属于同一逻辑题目的相关题目或回答 |
| 题目版本 | 区分同一逻辑题目在不同阶段形成的具体内容 |
| 版本历史或来源关系 | 为历史查询、版本追溯和旧版本恢复提供依据 |
| 题目所有权与分享关系 | 表达题目归属和其他用户的访问或使用权限 |
| 题库与题目的关联 | 支持题目保存、集中管理与再次选用 |
| 题目与问卷的使用关系 | 支持查询相关题目被哪些问卷使用 |

### 9.3 逻辑题目标识与具体题目标识的区别

具体题目标识用于定位某条题目记录；逻辑题目标识则用于识别同一逻辑题目在不同问卷或不同版本中的相关使用场景。

例如，不同问卷中可能分别存在“你的年龄”这一题目的具体记录。如果这些记录属于同一逻辑题目，就需要通过逻辑题目标识表达它们之间的关联，而不是仅依靠标题文字进行匹配。

在跨问卷统计中，接口使用 `question_key` 作为查询参数，以识别待统计的逻辑题目。

### 9.4 数据结构扩展的设计原则

本阶段的数据结构扩展遵循以下原则：

1. **保留原有核心数据组织方式。** 继续使用用户、问卷、题目和答卷等业务对象组织主要数据。
2. **不把所有数据放入一个集合。** 不同业务对象具有不同的生命周期和查询需求，应保持清晰的职责边界。
3. **谨慎处理题目复用和版本关系。** 题库更新不应无条件覆盖已发布问卷实际使用的题目内容。
4. **区分逻辑关联和物理存储。** 逻辑题目、版本和分享关系是业务概念，具体如何存储需要结合实际代码决定。
5. **由后端检查关联和权限。** 保存业务标识并不意味着数据库自动保证相应记录存在或当前用户有权访问。

因此，第二阶段主要是在原有数据结构上补充表达题目资源关系的能力，而不是推翻第一阶段整个数据库设计。

## 十、程序如何调整

第二阶段继续沿用第一阶段的 Flask 应用结构，在原有模块基础上扩展题目资源管理和统计处理能力。程序调整主要体现在题目库相关逻辑、跨问卷统计接口，以及相应自动化测试和文档的更新。

### 10.1 题目资源管理相关模块

### 10.2 跨问卷单题统计接口

本阶段在 `app/routes/responses.py` 中增加了跨问卷单题统计处理，接口为：

`GET /api/responses/question-stats/<question_key>`

它与第一阶段按单份问卷统计的接口不同，新增接口以逻辑题目标识作为查询入口，并在符合权限要求的问卷范围内汇总相关答卷。

从业务处理角度看，该功能需要完成以下工作：

1. 取得待统计的逻辑题目标识。
2. 确定当前用户有权统计的数据范围。
3. 查找与该逻辑题目相关的答卷和答案。
4. 根据题目类型计算对应的统计结果。
5. 返回统计数据。

以上步骤用于说明处理目标，不代表每一步都一定对应独立的数据库查询。具体数据库操作以当前 `responses.py` 中的实现为准。

## 十一、是否遇到兼容性问题

第二阶段是在已有系统上扩展功能，因此需要注意新旧数据标识、题目内容、统计范围和路由注册之间的兼容性。

### 11.1 逻辑题目标识与原有题目标识需要区分

第一阶段主要通过具体题目标识和 `survey_id` 管理问卷内题目。第二阶段的跨问卷统计则需要使用逻辑题目标识 `question_key` 关联同一逻辑题目。

如果把这两类标识混为一谈，就可能导致查询目标不正确、部分回答遗漏，或者不同题目被错误地归为同一题目。因此，新增统计功能需要明确使用逻辑题目标识，而原有问卷内题目管理仍需保留其原有标识用途。

### 11.2 题目版本变化可能影响已有问卷

题目复用和版本更新可能产生历史问卷内容保护的问题。如果所有问卷都直接读取同一份可变题目内容，修改题目就可能改变已发布问卷的题目定义。

为降低这一风险，数据设计需要区分题目资源、具体版本与问卷实际使用的题目内容，并遵循相应的版本规则。对于历史问卷，不能在没有明确业务约定的情况下，因题库更新而无条件改变其原有内容。

### 11.3 新增统计接口与原有问卷统计的范围不同

原有统计主要以 `survey_id` 为依据，查询某份问卷的提交记录。新增接口则以 `question_key` 为依据，在符合权限要求的多个问卷中汇总相关回答。

二者的统计范围和查询目标不同，因此应保留独立的处理逻辑，避免新功能修改原有问卷级统计的业务含义。

### 11.4 路由文件修改存在覆盖原有代码的风险

开发过程中，`app/routes/question_library.py` 曾发生错误覆盖。该文件之后根据用户提供的原始代码恢复，并对相关路由文件执行了语法检查。

## 十四、总结
